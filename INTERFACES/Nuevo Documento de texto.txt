## 2. REDISEÑO DE LA PANTALLA DE INICIO

La imagen proporcionada es la referencia visual principal de esta pantalla.

### Cambio fundamental

**La pantalla de Inicio no debe mostrar la barra lateral de navegación.**

La barra lateral solo debe aparecer cuando el usuario ingrese a alguno de los tres módulos de cálculo.

En Inicio, utiliza el ancho completo de la ventana.

### Distribución requerida

**Encabezado superior**

- Logotipo o nombre DIROPE Calc.
- Configuración de decimales.
- Acceso discreto a ajustes.

**Contenido principal**

Mostrar únicamente tres tarjetas funcionales:

1. Productividad de un factor.
2. Productividad multifactor.
3. Capacidad y personal.

Cada tarjeta debe permitir abrir directamente el módulo correspondiente.

No mostrar nuevamente los mismos tres módulos en un menú desplegable de «Nuevo cálculo».

Las tarjetas ya cumplen la función de iniciar un cálculo.

**Historial de cálculos**

Incorporar una sección compacta denominada «Cálculos recientes».

Mostrar solamente cálculos realmente guardados:

- Nombre del ejercicio.
- Tipo de cálculo.
- Fecha de última modificación.
- Opción para continuar.
- Acceso para administrar los cálculos guardados.

Si todavía no existen cálculos, mostrar un estado vacío discreto.

No incluir ejercicios ficticios ni fechas inventadas.

**Elemento visual**

Puedes utilizar una ilustración discreta de operaciones, análisis o gráficas, siguiendo la imagen de referencia.

Debe ser secundaria, no ocupar espacio que necesiten los controles y no afectar el rendimiento.

### Eliminar de Inicio

No incluir:

- Barra lateral.
- Menú desplegable redundante con los tres módulos.
- Botón «Ir al resultado».
- Botón «Exportar PDF».
- Paneles de resultados de ejercicios.
- Botones que repitan funciones de las tres tarjetas.
- Textos explicativos extensos.

La pantalla inicial debe funcionar como un selector de módulos y un punto de acceso a cálculos guardados.

## 3. NAVEGACIÓN DENTRO DE LOS MÓDULOS

Al ingresar a un módulo debe habilitarse la barra lateral.

La barra permite:

- Regresar al Inicio.
- Cambiar de módulo.
- Identificar el módulo activo.

Al regresar al Inicio, la barra debe ocultarse.

La transición no debe destruir los datos que el usuario está trabajando.

Al cambiar de módulo, conserva los borradores existentes.

Si el usuario inicia un cálculo nuevo y existe información sin guardar, solicita confirmación antes de reemplazarla.

No dupliques menús de selección innecesarios.

## 4. MEJORAR EL FLUJO DE RESOLUCIÓN

El sistema utiliza actualmente cinco etapas:

1. Planteamiento.
2. Datos.
3. Identificación.
4. Desarrollo.
5. Resultados.

Conserva esta organización general, pero hazla más flexible.

### A. Resolución guiada

El usuario debe poder avanzar normalmente por las etapas para revisar el procedimiento.

Esta modalidad debe conservar las fórmulas, sustituciones y resultados.

### B. Acceso directo al resultado

Añade dentro de cada módulo un botón:

**«Ver resultado»**

Debe estar disponible cuando los datos necesarios para resolver el problema sean válidos.

Funcionamiento:

1. El usuario selecciona el tipo de ejercicio.
2. Introduce los datos.
3. Presiona «Ver resultado».
4. El sistema valida los datos.
5. Ejecuta el cálculo correspondiente.
6. Genera el análisis necesario.
7. Abre directamente la pantalla de Resultados.

No obligues a recorrer todos los pasos si el usuario solamente necesita el resultado.

El resultado directo y el procedimiento guiado deben utilizar exactamente el mismo motor matemático.

Si los datos son incorrectos o insuficientes, muestra el error específico y conserva los valores registrados.

No habilites resultados incompletos ni omitas validaciones.

El enunciado y el título deben continuar siendo opcionales cuando los datos estructurados sean suficientes.

### C. Regresar al procedimiento

Desde Resultados debe poderse abrir el desarrollo matemático completo sin recalcular innecesariamente.

Al modificar una entrada, invalida los resultados anteriores y actualiza los nuevos cuando corresponda.

Nunca presentes resultados desactualizados.

## 5. ORGANIZACIÓN MATEMÁTICA DEL DESARROLLO

Actualmente ciertos ejercicios generan demasiados pasos y algunos resultados se presentan repetidamente.

Por ejemplo, el problema 1.14 de Charles Lackey y la comparación de Lakefront generan hasta 28 pasos de desarrollo.

Esto dificulta comprender el orden del procedimiento.

### Objetivo

Presentar los cálculos de manera jerárquica y respetando sus dependencias matemáticas.

Primero se deben calcular las variables necesarias para las operaciones posteriores.

### Ejemplo: productividad multifactor

Orden recomendado:

1. Identificación de la producción.
2. Cálculo de cada costo de recurso.
3. Obtención del costo total.
4. Cálculo de productividad.
5. Comparación con otro escenario, si existe.
6. Cambio porcentual.
7. Resultado e interpretación.

No presentar un cambio porcentual antes de calcular las productividades comparadas.

### Ejemplo: capacidad y personal

Orden recomendado:

1. Producción inicial.
2. Meta de producción.
3. Productividad laboral.
4. Horas-hombre requeridas.
5. Personal necesario.
6. Personal adicional o excedente.

### Eliminar redundancias

- No calcular dos veces la misma magnitud para el mismo escenario y los mismos datos.
- No repetir fórmulas idénticas cuando puedan reutilizarse resultados intermedios.
- No presentar indicadores secundarios como si fueran pasos principales obligatorios.
- No mezclar los resultados de escenarios diferentes.
- No mostrar operaciones que no corresponden al objetivo elegido.

**Importante:** no elimines un cálculo solo porque utiliza una fórmula similar. Dos escenarios diferentes pueden necesitar operaciones independientes.

### Niveles de detalle

Organiza la presentación en dos niveles:

**Procedimiento principal:** muestra las operaciones esenciales necesarias para obtener la respuesta.

**Detalle del cálculo:** permite desplegar operaciones auxiliares, costos individuales, participación de insumos u otras comprobaciones.

Esto permite conservar la trazabilidad matemática sin obligar al usuario a revisar decenas de pantallas.

Considera ampliar el modelo `Paso` con información de agrupación, prioridad o dependencias si mejora la arquitectura, manteniendo compatibilidad con los cálculos existentes.

## 6. RESULTADOS

Rediseña la pantalla de Resultados para presentar información sin redundancias.

Debe incluir:

- Nombre del caso.
- Resultado principal.
- Indicadores secundarios pertinentes.
- Unidades correctas.
- Comparación de escenarios, cuando corresponda.
- Gráfica pertinente, si existen datos.
- Interpretación breve.

Los resultados deben aparecer en orden lógico.

No mostrar tarjetas vacías, gráficas sin datos ni valores ficticios.

Mantén la precisión interna de los cálculos; el ajuste de decimales debe afectar únicamente su presentación.

### Acciones de Resultados

Incluir en esta pantalla:

- Ver procedimiento.
- Copiar informe.
- Exportar PDF.
- Guardar cálculo.

Estas opciones deben permanecer dentro del ejercicio, no en Inicio.

## 7. EXPORTACIÓN A PDF

Actualmente el proyecto permite copiar informes y exportar HTML mediante `src/dirope/informe.py`.

Conserva esas capacidades, pero añade exportación PDF directa.

### Requisitos

El botón «Exportar PDF» debe:

1. Aparecer en Resultados.
2. Abrir un cuadro para elegir ubicación y nombre.
3. Generar un archivo `.pdf` real.
4. Incluir datos, fórmulas, sustituciones, respuestas e interpretación.
5. Incluir la gráfica correspondiente cuando exista.
6. Utilizar páginas A4 verticales.
7. Manejar correctamente saltos de página, tablas y unidades.
8. Permitir abrir el PDF mediante un lector convencional.
9. Mostrar confirmación solamente después de guardar el archivo correctamente.

Utiliza un diseño técnico limpio:

- Fondo blanco.
- Texto negro.
- Tablas simples cuando correspondan.
- Encabezados discretos.
- Sin elementos decorativos innecesarios.

No generes un archivo HTML con extensión PDF.

Puedes utilizar una biblioteca estable como ReportLab si resulta necesaria. En tal caso, registra la dependencia, documenta su instalación y conserva el funcionamiento local sin conexión a internet una vez instalada.

Gestiona adecuadamente los errores de exportación y las dependencias faltantes.

Reutiliza los objetos de resultado existentes para producir tanto el informe copiable como el PDF.

- No se superpongan controles.
- Los tamaños mínimos sean razonables.

### B. Vista previa de resultados

Actualmente `previsualizar()` puede solicitar cálculos mientras se editan datos.

Centraliza la obtención del resultado para evitar cálculos duplicados e inconsistencias entre vista previa, desarrollo e informe.

Utiliza un único resultado válido para los mismos datos y recalcula únicamente cuando cambien los valores relevantes.

### C. Nombres de ejemplos

Revisa los nombres de los ejemplos precargados.

En particular, el caso 1.17 aparece registrado como «Natalie Attired», aunque el enunciado corresponde al taller de Susan Williams.

Corrige esta denominación y comprueba que cada ejemplo conserve sus datos originales.

### D. Diseño general

Mantén:

- Barra de navegación compacta en los módulos.
- Colores azul marino, blanco y azul claro.
- Tipografía coherente.
- Espaciado uniforme.
- Botones claramente identificables.

Evita:

- Cuadros repetidos.
- Barras de progreso duplicadas.
- Controles innecesarios.
- Grandes espacios vacíos sin propósito.
- Texto de ayuda permanente.
- Descripciones que el usuario no necesita para operar el programa.

Prioriza la filosofía de una interfaz estadística profesional: controles claros, datos visibles y resultados accesibles.
